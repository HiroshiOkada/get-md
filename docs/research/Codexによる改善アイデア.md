# Codexによる改善アイデア

## 前提

このプログラムは現在、Playwright の headless Chromium でページを描画し、`page.content()` で取得した HTML を `markdownify` に渡して Markdown 化している。実装が小さく扱いやすい一方で、速度面では「毎回ブラウザを起動する」こと、品質面では「ページ全体をほぼそのまま Markdown 化する」ことが主な制約になっている。

## 速度を上げる改善案

### 1. 複数 URL の一括処理を追加する

現在は 1 URL ごとに Playwright を起動して終了している。ブラウザ起動は重いので、複数 URL を処理する場合は 1 回だけ `browser` を起動し、ページまたは context を使い回すだけで大きく速くなる。

案:

- CLI に `get-md URL...` または `--input urls.txt` を追加する。
- `fetch_many()` を追加し、`sync_playwright()` と `browser` の寿命をバッチ全体に広げる。
- 同一 browser 内で複数 page を並列に開けるように `--concurrency` を追加する。

期待効果:

- 大量のページ変換で、ブラウザ起動時間を URL 数ぶん払わずに済む。
- サイトマップやドキュメント群の取得に使いやすくなる。

### 2. 静的 HTML 取得モードを追加する

JavaScript 描画が不要なページまで毎回 Playwright を使うと遅い。`httpx` などで通常の HTTP GET を試し、必要なときだけ Playwright にフォールバックするモードを追加すると速くなる。

案:

- `--mode auto|browser|http` を追加する。
- `auto` ではまず HTTP 取得し、本文が短すぎる、`noscript` 警告がある、主要コンテンツが空などの場合に Playwright へ切り替える。
- `browser` は現状どおり確実に JS 描画する。

期待効果:

- ブログ、ニュース、ドキュメントなど静的ページで大幅に高速化できる。
- Playwright のブラウザインストールが不要な用途も作れる。

### 3. 不要リソースをブロックする

Markdown 変換では画像バイナリ、フォント、動画、広告スクリプトの多くは不要。Playwright の routing で読み込みを止めると、ページロードが速くなり、余計な動的 UI も減る。

案:

- `--block-resources image,media,font` のようなオプションを追加する。
- デフォルトでは `font` と `media` をブロックし、画像 URL を Markdown に残したい場合は `image` は許可する。
- 広告・解析系ドメインの簡易ブロックリストを持つ。

期待効果:

- 重いページの取得時間と通信量を削減できる。
- Cookie バナーや広告枠由来のノイズが減る可能性がある。

### 4. 待機条件を賢くする

現在は `page.goto()` の後、指定された秒数だけ単純に待つ。ページによっては待ちすぎたり、逆に本文の遅延描画を取り逃がしたりする。

案:

- `--wait-until load|domcontentloaded|networkidle` を追加する。
- `article`, `main`, `[role=main]` などのセレクタが現れるまで待つ `--wait-for-selector` を追加する。
- 本文候補の文字数が一定以上になるまで短いポーリングを行う。

期待効果:

- 不必要な固定待ちを減らせる。
- SPA や遅延描画ページで本文の取り逃がしを減らせる。

### 5. ブラウザプロファイルとキャッシュを活用する

同じサイトを連続取得する場合、ブラウザキャッシュや Cookie を使うと速く、認証が必要なページにも対応しやすい。

案:

- `--user-data-dir PATH` を追加する。
- `--storage-state state.json` を追加し、ログイン済み状態を再利用できるようにする。
- キャッシュを使いたくない場合の `--no-cache` も用意する。

期待効果:

- 同一サイトの連続取得が速くなる。
- ログイン後に見えるドキュメントや管理画面の Markdown 化にも拡張しやすい。

## より意味のある Markdown を得る改善案

### 1. 本文抽出を導入する

現在は `body` 全体を Markdown 化するため、ヘッダー、ナビゲーション、フッター、広告、関連記事などが混ざりやすい。Markdown として使うなら、まず本文領域を抽出するのが最も効果が大きい。

案:

- `readability-lxml`、`trafilatura`、`jusText` などの本文抽出ライブラリを試す。
- 依存を増やしたくない場合は、`article`, `main`, `[role=main]`, `.content`, `.post`, `.entry-content` を優先する簡易抽出から始める。
- `--content-mode full|main|article` を追加する。

期待効果:

- ナビゲーションやフッターのノイズが減り、保存後に読み返しやすくなる。
- LLM に渡す入力としても意味密度が上がる。

### 2. Markdown の先頭にメタデータを付ける

取得元 URL、ページタイトル、取得日時が Markdown 内に残ると、後で出典確認や再取得がしやすい。

案:

- YAML front matter を追加する。
- `title`, `url`, `fetched_at`, `description`, `site_name`, `lang` を可能な範囲で入れる。
- `--front-matter/--no-front-matter` を追加する。

例:

```markdown
---
title: Example Page
url: https://example.com/page
fetched_at: 2026-08-30T10:00:00+09:00
description: ...
---
```

期待効果:

- Obsidian や静的サイトジェネレータ、検索インデックスで扱いやすくなる。
- Markdown 単体で由来が分かる。

### 3. 不要 UI 要素を削除するルールを増やす

`script` や `style` は削除されているが、実際のノイズは `nav`, `footer`, Cookie バナー、広告枠、共有ボタン、関連記事などにも多い。

案:

- デフォルト削除タグに `nav`, `footer`, `aside`, `form`, `button`, `iframe` を検討する。
- `aria-label`、`class`、`id` に `cookie`, `advert`, `promo`, `share`, `newsletter`, `related` などを含む要素を削除する。
- `--keep-nav` や `--full-page` で削除を抑制できるようにする。

期待効果:

- 本文以外のクリック導線や広告文言が混ざりにくくなる。
- 変換後の手作業修正が減る。

### 4. リンクと画像の扱いを選べるようにする

Markdown の用途によって、リンクを残したい場合、本文だけ欲しい場合、画像 URL も保存したい場合がある。

案:

- `--links inline|reference|strip` を追加する。
- 相対 URL を絶対 URL に正規化する。
- `--images keep|alt-only|strip` を追加する。
- 画像を残す場合は `alt` が空の画像を除外する。

期待効果:

- 読書用、アーカイブ用、LLM 入力用で出力を使い分けられる。
- 壊れた相対リンクが減る。

### 5. 見出し構造を整える

Web ページにはロゴやカード内タイトルのように、本文の見出しではない `h1` や `h2` が多い。これが Markdown のアウトラインを壊すことがある。

案:

- 本文抽出後、最初の主要タイトルを `#` に統一する。
- 見出しレベルが飛ぶ場合は補正する。
- 短すぎる見出し、同じ見出しの連続、ナビゲーション由来の見出しを除外する。

期待効果:

- Markdown エディタやアウトライン表示で読みやすくなる。
- 章立てが意味のある構造になる。

### 6. テーブルとコードブロックを改善する

`markdownify` の標準変換だけでは、複雑な表やコードブロックの言語情報が失われることがある。

案:

- `pre > code` の class から言語名を拾い、フェンスコードに反映する。
- テーブルは Markdown テーブルに向かない複雑なものを HTML のまま残す選択肢を用意する。
- `--preserve-html table,details` のように一部タグを保持できるようにする。

期待効果:

- 技術記事や仕様書の変換品質が上がる。
- 表の崩れによる情報欠落を防ぎやすい。

### 7. Markdown 後処理を強化する

現在の後処理は連続空行の圧縮だけなので、Web 由来の細かいノイズが残る。

案:

- 行末スペースの削除。
- 空リンク、空強調、空見出しの削除。
- 同じリンクテキストやパンくずの繰り返し削除。
- 連続する箇条書きの不自然な空行を補正する。
- `#`, `*`, `_` などの過剰エスケープを必要に応じて調整する。

期待効果:

- Markdown として自然に読める出力に近づく。
- 差分管理したときのノイズも減る。

## 実装順のおすすめ

1. 本文抽出とノイズ除去を先に入れる。
2. メタデータ front matter を追加する。
3. 待機条件とリソースブロックで単発取得を速くする。
4. 複数 URL の一括処理と browser 再利用を入れる。
5. 静的 HTTP 取得モードを追加する。

理由は、ユーザーが最初に体感しやすいのは「Markdown が読みやすくなること」で、その次に「複数ページで速くなること」だから。特に本文抽出は実装範囲が比較的小さい割に、出力品質への効果が大きい。

## 最初に着手するなら

最初の実装候補は `to_markdown()` の前処理を強化すること。

- `main`, `article`, `[role=main]` を優先して root にする。
- `nav`, `footer`, `aside`, `form`, `button`, `iframe` を削除する。
- Cookie、広告、共有、関連記事、ニュースレターらしい class/id を持つ要素を削除する。
- `title` と URL を front matter に入れる。

この変更なら CLI 全体の構造を大きく変えずに、意味のある Markdown への改善を先に出せる。その後、`fetcher.py` を browser 再利用や HTTP fallback に拡張していくのがよい。
