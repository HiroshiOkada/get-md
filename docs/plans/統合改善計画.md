# get-md 統合改善計画

## 1. 目的

Codex、OpenCode、Antigravity の3案を、現在の実装に照らして統合した計画である。
目標は次の2点とする。

1. Webページから、出典と構造を保った、ノイズの少ない Markdown を生成する。
2. 単一ページでは不要な通信と待機を減らし、複数ページではブラウザを再利用して高速化する。

一度に大きく書き換えず、各段階でテストと計測を行う。品質を落として得た速度は改善とみなさず、
本文抽出に失敗した場合は必ず安全なフォールバックを使う。

## 2. 3案を比較した結論

### 優先して採用する案

3案で共通しており、効果と実現性が高いものを中核にする。

| 改善 | 判断 | 理由 |
| --- | --- | --- |
| 本文抽出とノイズ除去 | 最優先 | Markdown の意味密度に最も効く |
| 相対 URL の絶対化 | 最優先 | 低コストでリンク切れを防げる |
| YAML front matter | 採用 | 出典、再取得、検索、LLM利用に有効 |
| 非表示要素の除去 | 採用 | メニュー、モーダル、重複テキストを減らせる |
| 不要リソースのブロック | 採用 | Playwright の通信量と待ち時間を減らせる |
| 固定待機の改善 | 採用 | 待ちすぎと本文取得漏れの両方を減らせる |
| タイムアウト時の部分取得 | 採用 | 取得済み DOM を無駄にしない |
| コードブロックの言語保持 | 採用 | 技術文書の意味を保つ |
| 複数 URL とブラウザ再利用 | 採用 | バッチ処理で大きな効果がある |
| HTTP/Playwright 自動切替 | 採用 | 静的ページの高速化に有効。ただし判定精度を検証する |
| リンク・画像ポリシー | 採用 | 読書、保存、LLM入力で用途が異なるため |
| 変換テストとベンチマーク | 最初に採用 | 改善による情報欠落と速度低下を検知するため |

### 条件付きで採用する案

| 改善 | 条件・注意点 |
| --- | --- |
| `networkidle` 待機 | 常時通信するサイトでは終わらないため、既定値にせず明示指定時のみ使う |
| 画像ブロック | DOM の `src` は通常残るが遅延画像に影響し得る。既定値は計測後に決める |
| CSS ブロック | JS の表示判定やスクリーンショットを壊すため既定では行わない |
| Readability/Trafilatura | 記事には強いが、API資料、表中心ページ、一覧では欠落し得る。抽出評価と fallback を必須にする |
| 高速 HTML パーサー | BeautifulSoup が実測上のボトルネックになった場合だけ変更する |
| persistent context | キャッシュと認証には有効だが状態混入の危険がある。明示オプションで提供する |
| 結果キャッシュ | 鮮度、認証、Cookie 依存の扱いを決めてから追加する |
| 数式・複雑な表の復元 | ページ実装ごとの差が大きいため、代表 fixture を揃えてから進める |

### 当面は見送る案

| 改善 | 見送る理由 |
| --- | --- |
| 常駐サーバー `--serve` | CLI の運用・終了処理・セキュリティを複雑にする。まずバッチ再利用で効果を確認する |
| headless shell の固定利用 | 環境差と Playwright バージョン差があり、主要なボトルネック解消より優先度が低い |
| 変換結果の自動折り返し | 日本語やコード、表を壊しやすく、意味改善への寄与が小さい |

## 3. 目標アーキテクチャ

処理を「取得」と「変換」に分けた現在の構造は維持し、境界のデータを明確にする。

```text
CLI options
    |
    v
Fetcher: HTTP fast path -> 必要な場合だけ Playwright fallback
    |
    v
FetchResult(html, requested_url, final_url, title, fetch_method, elapsed)
    |
    v
Normalizer: URL絶対化、非表示・明白なノイズの除去
    |
    v
Extractor: main/article/readability候補を評価 -> 不適切なら body fallback
    |
    v
Converter: Markdown化、コード言語・表・リンク・画像ポリシー
    |
    v
Metadata + post-processing -> file/stdout
```

主な設計方針は次の通り。

- `fetch()` は文字列だけでなく `FetchResult` を返せる形へ段階的に移行する。
- `to_markdown()` は `base_url` と変換オプションを受け取り、I/Oを行わない純粋関数に保つ。
- 本文抽出結果は無条件に信用せず、文字数、段落数、リンク密度、見出しやコード・表の保持状況で評価する。
- 抽出結果が短すぎる、リンクだけになる、元本文との差が極端な場合は `main` または `body` に戻す。
- CLI の既存オプションは維持し、新機能は互換性のある形で追加する。

## 4. 実装ロードマップ

### Phase 0: 品質基準と計測基盤

最初に、後続変更の良し悪しを判定できる状態を作る。

- `pytest` を開発依存に追加する。
- `tests/fixtures/` にネットワーク不要の HTML fixture を置く。
- `converter.py` のスナップショットまたは golden-file テストを作る。
- フェッチャーは Playwright の page/browser をモックせず、ローカル HTTP サーバーを使う統合テストを少数用意する。
- `python -m pytest` と `ruff check .` を標準検証コマンドにする。
- 変換時間、取得時間、出力文字数、リンク数を記録できる小さなベンチマークを追加する。

fixture は最低限、静的記事、SPA相当、技術文書、相対リンク、遅延画像、コード、単純な表、
ナビゲーションが多いページ、`main` がないページ、日本語ページ、壊れた HTML を含める。

完了条件:

- 現行出力を固定する回帰テストがある。
- 速度と出力品質を変更前後で同じ入力に対して比較できる。

### Phase 1: 低リスクな Markdown 正確性改善

依存ライブラリを増やさず、明確に正しい変換を先に実装する。

1. `to_markdown(html, *, base_url=None, options=None)` に拡張する。
2. `href`, `src`, `srcset`, canonical URL を `urljoin()` で絶対化する。
3. `[hidden]`, `aria-hidden="true"`、明示的な `display:none` を除去する。
4. `role=navigation|banner|contentinfo|dialog` と、cookie/consent/advert/share 等の明白なノイズを除去する。
5. 空リンク、空見出し、空画像、行末空白、過剰な空行を整理する。
6. `pre > code` の `language-*`, `lang-*`, `data-language` を fenced code block に保持する。
7. `title`, `description`, canonical URL, author, published time, language, fetched time を抽出する。
8. YAML は文字列連結で組み立てず、YAMLライブラリまたは安全な引用処理を使う。

CLI には以下を追加する。

```text
--front-matter / --no-front-matter
--links keep|text|strip
--images keep|alt|strip
--content full|main
```

互換性確保のため、最初のリリースでは front matter は明示指定で有効にする。
本文抽出が十分に検証できた時点で、次のマイナーバージョンから `--content main` を既定にする。

完了条件:

- 相対リンクと画像 URL が出力先に関係なく解決できる。
- 非表示テキストと既知の UI ノイズが fixture から消える。
- コード本文とコード言語が欠落しない。
- 従来相当の出力は `--content full --no-front-matter` で得られる。

### Phase 2: 本文抽出とフォールバック

Markdown の意味密度を最も大きく改善する段階。

1. まず依存なしの候補選択を実装する。
   `article`, `main`, `[role=main]` と一般的な content class を候補にする。
2. 各候補を、本文文字数、段落数、リンク密度、句読点密度、見出し・コード・表の数で採点する。
3. 記事抽出ライブラリを1つだけ比較導入し、タイトル、本文、コード、表の保持率を fixture で評価する。
4. ライブラリ抽出結果が基準未満なら DOM 候補、さらに失敗なら `body` へ戻す。
5. 抽出方法を `auto|dom|readability|full` から選べるようにする。
6. `--debug-extraction` では選択した方式、候補スコア、fallback 理由を stderr に出す。

ライブラリは名前だけで決定せず、`trafilatura` と `readability-lxml` を同じ fixture で比較する。
依存サイズ、Python 3.14 対応、コード・表・画像の保持、処理時間を評価し、優れた方だけを採用する。

完了条件:

- 記事 fixture でヘッダー、フッター、広告、関連記事が除去される。
- API資料、コード中心ページ、表中心ページで主要情報が欠落した場合は full fallback が働く。
- 抽出失敗が例外ではなく、説明可能な fallback として処理される。

### Phase 3: Playwright の単発取得高速化

出力を変えずに取得時間を減らす。

1. `wait_until` を `domcontentloaded|load|networkidle|commit` から選択可能にする。
2. 既定は `domcontentloaded` とし、その後に短く上限付きの本文安定待機を行う。
3. `--wait-for-selector` と既存 `--wait` を併存させる。固定待機は最終手段として残す。
4. スクリーンショットがない場合、まず `font` と `media` をブロックする。
5. `image` ブロックは A/B 計測後に既定値を決める。`stylesheet`, `script`, `xhr`, `fetch` は既定で許可する。
6. 広告・解析ドメインの遮断は小さく保ち、ユーザーが解除できるようにする。
7. navigation timeout 後も page が存在すれば `page.content()` を試す。`--strict` では従来通り失敗にする。
8. スクリーンショット時は表示に必要なリソース遮断を自動的に解除する。

CLI には以下を追加する。

```text
--wait-until domcontentloaded|load|networkidle|commit
--wait-for-selector SELECTOR
--block-resources TYPE[,TYPE...]
--strict
```

完了条件:

- fixture サーバーでリソース遮断の有無を比較し、本文 DOM が同一である。
- スクリーンショット利用時の表示が現状より劣化しない。
- タイムアウトしたページでも取得済み本文を返せる。
- 単発ベンチマークで cold start と navigation を分けて記録する。

### Phase 4: 複数 URL、ブラウザ再利用、非同期化

ブラウザ起動コストを複数ページで共有する。

1. URL引数を複数受け取れるようにし、`--input FILE` も追加する。
2. ブラウザはバッチにつき1回起動し、URLごとに独立した context または page を使う。
3. `playwright.async_api` に移行し、`--concurrency` で同時実行数を制限する。
4. 結果順は入力順で安定させ、1件の失敗で全件を中止しない。
5. 単一 URL の既存 CLI 動作と出力ファイル名は維持する。
6. 複数 URL で `-o` が指定された場合は出力ディレクトリとして扱い、名前衝突を検出する。
7. 進捗、保存先、警告はすべて stderr に出し、stdout は Markdown または機械可読結果専用にする。

CLI には以下を追加する。

```text
get-md URL [URL ...]
--input FILE
--concurrency N
--output-dir DIR
```

完了条件:

- N件の取得で Chromium 起動が1回だけである。
- 同時実行数が指定値を超えない。
- 失敗 URL と成功 URL を終了時に区別して報告する。
- 逐次実行よりバッチ実行が代表ケースで高速である。

### Phase 5: HTTP fast path

静的ページでは Playwright 自体を起動しない。

1. HTTP クライアントを追加し、redirect 後の URL、文字コード、content type、圧縮を正しく扱う。
2. `--fetch auto|http|browser` を追加する。
3. `auto` では HTTP HTML を変換候補として評価し、十分ならそのまま使う。
4. 本文が極端に短い、JS必須メッセージだけ、root shell しかない、主要 DOM が空の場合は browser に戻す。
5. HTTP と browser の二重取得率を記録し、auto 判定を fixture と実サイトベンチマークで調整する。
6. robots、認証、Cookie、User-Agent、リダイレクトの挙動を両方式で可能な限り揃える。

完了条件:

- 静的 fixture は Chromium を起動せずに同等の本文を生成する。
- SPA fixture は自動的に browser fallback する。
- `--fetch http` と `--fetch browser` で利用者が判定を上書きできる。
- auto の二重取得によって browser 直行より遅くなるケースを計測し、許容範囲を定める。

### Phase 6: 高度な品質と運用機能

利用実績と fixture を増やしてから、情報形式ごとの品質を上げる。

- rowspan/colspan/入れ子を含む表は、GFM変換と HTML保持を選択可能にする。
- MathJax/KaTeX について、元 TeX を確実に取得できる形式だけ復元する。
- `details`, `figure`, `figcaption`, `blockquote` の変換を改善する。
- `--storage-state` または明示的な profile directory で認証状態を再利用する。
- ETag、Last-Modified、TTLを持つ opt-in キャッシュを検討する。
- parser のCPU時間が支配的になった場合だけ `lxml` または `selectolax` を比較する。

## 5. テスト戦略

### 単体テスト

- URL絶対化: 相対、protocol-relative、fragment、`mailto:`, `data:`。
- メタデータ: title/OG/canonical の優先順位と YAML 特殊文字。
- ノイズ除去: hidden、ARIA role、cookie banner。通常本文の誤削除も検査する。
- コード: 言語あり・なし、入れ子、バッククォートを含むコード。
- 出力パス: Unicode、query、末尾 slash、同名 URL。

### 統合テスト

- 静的 HTTP、redirect、文字コード、404、timeout。
- JSで後から本文を追加するページ。
- 常時通信して `networkidle` にならないページ。
- 遅延画像と screenshot の組み合わせ。
- バッチの一部失敗、順序維持、同名ファイル衝突。

### 回帰テスト

実サイトの HTML を利用規約に反しない範囲で保存または最小化し、ネットワークに依存しない fixture にする。
取得時刻や広告IDなどの変動部分を除き、Markdown の意味的な差分をレビューできるようにする。

## 6. 評価指標

### 品質

- 主要本文、見出し、コード、表、リンクが保持されているか。
- ナビゲーション、フッター、広告、Cookie文言の比率が減ったか。
- 相対リンクが残っていないか。
- front matter だけで出典 URL、タイトル、取得日時を特定できるか。
- fallback が発生した理由をデバッグ出力で説明できるか。

自動指標だけでは本文の意味を判定できないため、代表 fixture では golden diff と目視レビューを併用する。

### 性能

- cold browser start、navigation、DOM取得、変換を別々に計測する。
- 単一 URL は中央値と p95、バッチは総時間と1 URLあたり時間を記録する。
- HTTP fast path の成功率、browser fallback 率、二重取得率を記録する。
- 高速化前後で本文文字数、コード数、表数、リンク数が意図せず減っていないことを確認する。

固定の「何%高速化」を先に約束せず、同じ環境・同じ fixture の基準値に対する改善で判断する。

## 8. 最初の実装スプリント

最初の変更は P0-1、P0-2、P1-1 に限定する。

1. テスト基盤と代表 fixture を作る。
2. 現行 `to_markdown()` の出力を golden test として固定する。
3. `base_url` を追加し、リンクと画像 URL を絶対化する。
4. 非表示要素と誤判定しにくいノイズだけを除去する。
5. 変更前後の出力と変換時間を比較する。
6. README に新しい動作と、従来相当出力の指定方法を記載する。

この順序なら、すぐに正しさを改善しつつ、本文抽出・ブラウザ高速化・HTTP fast path を
安全に進めるための土台ができる。

## 9. 全体の完了条件

- 通常の記事では本文中心の Markdown が既定で得られる。
- 技術資料や表中心ページでは、抽出失敗による情報欠落を fallback で回避できる。
- 出典、タイトル、取得日時を Markdown に保持できる。
- 単一取得、バッチ取得、静的 HTTP、JS描画の各経路に自動テストがある。
- バッチではブラウザを再利用し、静的ページでは browser を省略できる。
- すべての高速化について、出力品質を保った計測結果が残る。
- CLIヘルプと README が実装済みオプションだけを正確に説明している。
